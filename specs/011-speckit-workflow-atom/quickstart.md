# Quickstart: Adopting a Speckit Workflow Atom (simplified)

**Feature**: Spec 011 (simplified, PR #54 merged)
**Audience**: satellite operators adopting a workflow atom; downstream tooling authors verifying reader consistency.

## Prerequisites

- `haex` CLI installed and functional (Spec 007 + Spec 008 landed).
- A project already using haex-hive: a valid `.haex-hive.json` (v2 shape) is present and the operator can already run `haex install`.
- A publisher clone of the workflow atom's source repository is reachable under `$HAEX_HIVE_STATE/repos/`.
- Any speckit-community extensions the workflow atom declares as `required_extensions[]` are already installed under `.specify/extensions/<extension-id>/` at a compatible version. `haex install` reads their `extension.yml` `version` field as authoritative.

## 1. Set up the consumer-owned local source

If the project already has extension declarations the operator wants to preserve, move them into `.specify/extensions.local.yml` BEFORE adopting a workflow atom. This file is consumer-owned; `haex install` never modifies it.

Example `.specify/extensions.local.yml`:

```yaml
installed:
  - acme-internal-linter

settings:
  llm_endpoint: "http://localhost:8080"

required_extensions:
  - id: acme-internal-linter
    version_constraint: ">=2.0.0"

hooks:
  before_specify:
    - extension: acme-internal
      command: acme.internal.spec-guard
      script: hooks/local/spec-guard.sh
      description: "ACME internal spec-guard check"
      enabled: true
      optional: false
```

Absent file = empty local declarations; the install still works.

## 2. Adopt the workflow atom

Edit `.haex-hive.json`:

```json
{
  "haex_hive_version": "2",
  "identity": "com.github.example.consumer",
  "atoms": [
    {
      "source": "https://github.com/example/speckit-workflows",
      "revision": "aabbccddeeff00112233445566778899aabbccdd",
      "includes": ["com.example.publisher.strict-tdd-workflow"]
    }
  ]
}
```

`revision` MUST be a full 40-char SHA (Principle IV). Only ONE atom may carry `contributes.speckit_workflow`. Adopting two refuses at install time (see Step 7).

## 3. First install

Because the atom contributes a `constitution.md` fragment, the review-gated multi-source merge path applies even when this is the only constitution contribution. The installer MUST route this case through `assemble_multi_source`, not the `assemble_single_source` shortcut:

```console
$ haex install --llm=file
# exits with code 5 and writes .haex-hive/constitution.merge.pending.json

$ # review pending merge; produce a merged constitution candidate

$ haex install --accept-merged /path/to/merged-candidate.md
installed generation g_20260902T160000Z_ab12
```

Atoms without a constitution fragment use plain `haex install` (no `--llm=file` step).

The US1 integration test verifies this contract by asserting exit code `5`, the
presence of `.haex-hive/constitution.merge.pending.json`, and the absence of
new workflow publication before the merge is accepted. After
`--accept-merged`, it verifies the workflow files and merged constitution.

## 4. Verify the publication

After a successful install:

```console
$ ls .specify/workflows/
com.example.publisher.strict-tdd-workflow/
speckit/

$ ls .specify/workflows/com.example.publisher.strict-tdd-workflow/
workflow.yml

$ ls .specify/extensions/workflow-atoms/
com.example.publisher.strict-tdd-workflow/

$ ls .specify/extensions/workflow-atoms/com.example.publisher.strict-tdd-workflow/
pre-implement.sh
post-tasks.sh
```

The atom's constitution fragment lands in `.haex-hive/constitution.md`:

```markdown
## Workflow-Contributed Rules

### From atom `com.example.publisher.strict-tdd-workflow` (revision `aabbccdd`)

<the atom's constitution.md content verbatim>
```

The generated `.specify/extensions.yml` merges local + atom declarations:

```yaml
# generated by haex install: do not edit; edit .specify/extensions.local.yml or adopt a workflow atom instead

required_extensions:
  - id: acme-internal-linter          # from local source
    version_constraint: ">=2.0.0"
    sources:
      - origin: local
        kind: required
  - id: v-model-extension-pack        # from atom
    version_constraint: ">=0.7.2"
    sources:
      - origin: atom
        atom_id: com.example.publisher.strict-tdd-workflow
        ...
```

Notice: the consumer-owned `.specify/extensions.local.yml` is unchanged; `haex install` NEVER writes to it.

## 5. Verify the binding

Query which workflow is binding:

```python
from pathlib import Path
from haex_hive.workflow.resolver import resolve_active_workflow

resolution = resolve_active_workflow(Path.cwd())
assert resolution.source == "atom"
assert resolution.atom_id == "com.example.publisher.strict-tdd-workflow"
assert resolution.workflow_path.name == "workflow.yml"
```

No manual selector step; adoption implies binding.

## 6. Refusal path: required extension missing

If the workflow atom declares `required_extensions: [{id: v-model-extension-pack, version_constraint: ">=0.7.2"}]` and the extension is absent under `.specify/extensions/`:

```console
$ haex install
error: exit=4 key=required-workflow-extension-missing
  workflow atom `com.example.publisher.strict-tdd-workflow` requires
  extension `v-model-extension-pack` version `>=0.7.2`; not installed under
  .specify/extensions/
  hint: install the extension via `speckit extensions install v-model-extension-pack@0.7.2`
```

Install refuses BEFORE any file publication. Fix by installing the extension and retrying.

## 7. Refusal path: two workflow atoms adopted

If `.haex-hive.json` names two atoms both carrying `contributes.speckit_workflow`:

```console
$ haex install
error: exit=2 key=multiple-workflow-atoms-refused
  more than one adopted atom declares contributes.speckit_workflow:
    - com.example.publisher.strict-tdd-workflow (github.com/example/speckit-workflows)
    - com.other.publisher.bugfix-workflow (github.com/other/workflows)
  hint: adopt at most one speckit-workflow atom per project
```

Install refuses after resolving and validating the selected publisher atom
manifests, but before loading fragments or publishing any file.

## 8. Downgrade

Remove the workflow atom from `.haex-hive.json.atoms[]` and re-install:

```console
$ haex install
installed generation g_20260902T170000Z_bd41
```

The atom's files are gone:

```console
$ ls .specify/workflows/
speckit/

$ ls .specify/extensions/workflow-atoms/
(empty)
```

The `## Workflow-Contributed Rules` section vanishes from `.haex-hive/constitution.md`. The generated `.specify/extensions.yml` reduces to the operator's local declarations only. `.specify/extensions.local.yml` is byte-identical to before.

The reader helper now reports the bundled workflow:

```python
resolution = resolve_active_workflow(Path.cwd())
assert resolution.source == "bundled"
assert resolution.atom_id is None
```

## 9. Where things live (recap)

- **In the repo checkout** (committed):
  - `.haex-hive.json`: adoption declarations (Spec 007).
  - `.specify/workflows/<atom-id>/workflow.yml`: adopted workflow atom's workflow declaration (Spec 011).
  - `.specify/extensions/workflow-atoms/<atom-id>/`: adopted workflow atom's hook scripts (Spec 011, reserved namespace).
  - `.specify/extensions.local.yml`: consumer-owned local extensions declarations (Spec 011, NEVER touched by runtime).
  - `.specify/extensions.yml`: generated merge output (Spec 011, regenerated every install).
  - `.haex-hive/constitution.md`: merged constitution including `## Workflow-Contributed Rules` (Spec 011).
  - `.haex-hive/install.lock`, `.haex-hive/visibility.json`: install transaction outputs (Spec 008).
- **Under `$HAEX_HIVE_STATE`** (device-local):
  - `repos/<clone-hash>/`: publisher clones (Spec 007).
  - `locks/<repo-key>/install.mutex`: install exclusive lock (Spec 008).

## Out of scope

- Authoring a workflow atom: covered under publisher tooling / a Spec 011 successor doc.
- Installing speckit-community extensions: delegated to specifyr; `haex install` refuses when required ones are missing.
- Runtime enforcement of workflow adherence: constitution advisory-to-agent; a mechanical gate is deferred to a Phase-7 successor spec.
